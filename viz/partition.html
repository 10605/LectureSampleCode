Shuffle-Sort In Map-Reduce

A map step is embarrassingly parallel — each worker rewrites its own keys and never talks to anyone. The moment those keys have to be grouped so that each worker sees everything in a group, data may need to be moved between workers. That move is the shuffle, and it is the expensive part of MapReduce. Here it is in slow motion, over k workers, with one round of the wondrous-numbers map — n ↦ n/2 if even else 3n+1, emitting nothing once a key falls into the final 4 → 2 → 1 → 4 ... cycle.

    The partition function much be deterministic and balanced. Every worker must compute the same destination for a key, or the grouping breaks. You can also have a null hash, so each key is sent to worker key mod k. Why is that a bad choice here?

    When is data sorted? Here each worker sorts its own outgoing partitions locally, so the receiver gets k already sorted runs and only has to merge them. This is how Hadoop works but other choices are possible: e.g., data can be sorted after it is received (as in Google's MapReduce) or grouped without a full sort (Spark's approach).

    What this leaves out. There's no reducer in this algorithm (and no combiner). In general the mapper and reducer workers can be distinct and there can differing numbers of them. What would be a reasonable reduce operation for this task?
