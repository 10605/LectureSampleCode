Word Count In Map-Reduce

Word count is the Hello, world of MapReduce, and it is also the smallest program in which every interesting part of the system shows up. The map — document ↦ (word, 1) for each token — is embarrassingly parallel: no worker needs to see another worker's documents. But the sum for toast cannot be computed until every (toast, 1) in the corpus sits on one machine, and that gathering is the shuffle. Here it is in slow motion over a four-document corpus, with a combiner you can switch on and a partitioner you can make bad.

    The partition function must be deterministic and balanced. Every mapper must compute the same destination for a word, or the grouping breaks and toast gets counted twice. The default here is the naive choice — send a word to worker (first letter) mod k. It is deterministic, so it is correct; look at the reducer load and say why it is still a bad choice, and what happens to it on a real English corpus.

    The combiner is a reducer that runs on the mapper, on that mapper's output only. Switch it on and watch the number of pairs crossing the network fall. It is legal here because addition is associative and commutative — a combiner is an optimization the framework may run zero, one, or many times, so a job whose answer depends on it running is a buggy job. Which of these reducers could not be used as its own combiner: sum, max, count-distinct, mean?

    When is data sorted? Each worker sorts its own outgoing partitions locally, so the receiver gets k already sorted runs and only has to merge them — and after the merge, every occurrence of a word is adjacent, which is exactly the input the reducer wants. This is how Hadoop works; Google's MapReduce sorts after receiving, and Spark can group without a full sort.
